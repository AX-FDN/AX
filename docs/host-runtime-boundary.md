# AX Host Runtime Boundary

最后更新：2026-04-24

这份文档只回答一个问题：

AX 当前哪些能力应该放在编译器内建宿主层，哪些能力应该留给 AX 自己去表达。

## 当前分层

AX 现在有两层：

1. Rust 宿主运行时
   位置：
   - `src/interpreter.rs`
   - `src/semantic/checker/builtin.rs`

   责任：
   - 接操作系统和宿主环境
   - 提供最小 builtin 能力
   - 给出稳定 diagnostics

2. AX 脚本层
   位置：
   - `examples/`
   - 后续真正的 AX 库代码

   责任：
   - 组合 builtin 做真实工具逻辑
   - 承担流程、规则、策略和报告生成
   - 尽量把“业务层”和“工具层”逻辑留在 AX 本身

一句话：

Rust 负责把宿主世界接进来。
AX 负责把这些原语组合成真正的工具。

## 用户不应该看到什么

对 AX 用户来说，不应该形成下面这种心智模型：

- “我写的是 AX，但我实际在下载一堆 Rust 包”

当前更准确的模型应该是：

- 用户安装的是 `axc` / AX toolchain
- 用户调用的是 AX 暴露出来的标准接口
- 这些接口当前可以由 Rust 宿主层实现
- 但 Rust crate 属于实现细节，不属于用户直接消费的标准库界面

一句话：

- 内部可以是 Rust
- 外部必须表现为 AX

## 官方接口层和实现层怎么分

当前推荐把库边界拆成四层：

1. Rust 宿主原语层
   位置：
   - `src/interpreter.rs`
   - `src/semantic/checker/builtin.rs`

   作用：
   - 接操作系统
   - 接文件系统、路径、环境变量、进程
   - 给出稳定 diagnostics

   对外边界：
   - 不直接作为“AX 用户下载的包”
   - 不把 Rust crate 名字直接暴露成 AX 的包名和依赖模型

2. AX 官方接口层
   当前还是方向，不是完整成品。

   推荐承接：
   - `std`
   - `sys`
   - `foundation`

   作用：
   - 把宿主原语收敛成 AX 视角的稳定接口
   - 提供共享 helper，而不是让每个项目都重新拼一遍
   - 成为后续模块 / import / 包系统稳定后的正式地基

3. 项目库层
   位置：
   - 项目自己的 `lib/`
   - `AX.toml` 的 `sources = [...]`

   作用：
   - 放项目私有 helper
   - 放业务规则、流程、报表、文本策略
   - 不承诺跨项目稳定

4. 实验层
   推荐承接：
   - `network`
   - `concurrency`
   - 还没有证据证明应该进入主线的宿主扩展

   作用：
   - 快速试错
   - 不污染主标准库面
   - 不绑死当前运行时模型

## 哪些东西适合留在主仓库

当前阶段，下面这些东西更适合放在 AX 主仓库里：

- Rust 宿主原语实现
- builtin 的类型检查与 diagnostics
- AX 官方标准接口定义
- AX 官方共享基础库
- 对应的 examples / docs / benchmark / tests

原因：

- 当前语言接口还在演进
- builtin、diagnostics、examples 和 benchmark 需要一起收口
- 还没有稳定外部包管理
- 如果现在分仓库，版本同步成本会很高

## 哪些东西可以放在你自己的仓库

下面这些东西可以放在你自己的仓库里：

- 项目私有 AX helper
- 只服务单个工具或单个业务域的库
- 基于当前 builtin 组合出来的高层流程代码
- 网络 / 并发 / 其他高风险方向的实验实现

但不建议现在就把下面这些拆成个人独立仓库：

- 官方 `std / sys / foundation` 边界
- 编译器 builtin 对应的正式 AX 接口
- 需要和 diagnostics / benchmark 一起演进的核心能力面

## 推荐的仓库归属规则

现在可以直接按这条规则执行：

1. 如果它是操作系统原语或宿主桥接能力，就留在 AX 主仓库，用 Rust 实现。
2. 如果它是官方准备长期收口的 AX 标准接口，也留在 AX 主仓库。
3. 如果它只是你当前项目的 helper，就放项目仓库。
4. 如果它会显著拉大运行时和语义表面积，比如网络、并发、FFI 扩展，就先放实验目录或实验仓库。

## 当前最缺的不是更多 builtin，而是共享 AX 库层

从当前仓库的样例看，缺口已经不是“完全没有宿主能力”，而是：

- 已经有 `argv / env / path / fs / process / string` 原语
- 但还没有把它们收成一层共享 AX 基础库

这会直接导致：

- 多个样例重复写 `file_kind`
- 多个样例重复写 `text_stats`
- 多个样例重复写 report 拼接和 CLI 参数检查

所以当前最值钱的推进顺序应该是：

1. 继续把 Rust 宿主原语保持在最小可用面
2. 优先抽 AX 侧共享基础库，比如：
   - `foundation/text`
   - `foundation/report`
   - `foundation/cli`
   - `foundation/workspace`
3. 每补一层共享库，就补一个更真实的 AX 工具样例

## 未来包系统的默认口径

在真正的 AX 包系统稳定前，默认口径应当是：

- AX 用户依赖的是 AX 包
- Rust crate 不是 AX 用户直接消费的依赖单位
- 如果未来存在 Rust 写的宿主扩展，也必须先收敛成 AX 暴露的稳定接口，再谈对外分发

也就是说，未来即使底层实现继续用 Rust，用户看到的也应该是：

- AX 标准库
- AX 官方扩展
- AX 项目库

而不是：

- “下载一个 Rust crate，然后在 AX 里直接拿来用”

## 哪些能力应该放在宿主层

只有这几类能力应该优先放在 builtin / host runtime 里：

- `argv`
- `env`
- `path`
- `fs`
- `process`
- 极少量基础 `string` 辅助

判断标准：

- 不接宿主就根本做不了
- 不先做这个原语，AX 连最小工具闭环都起不来
- 做成 builtin 后，能让 AX 层马上多写出一种真实工具样例

当前已经属于这一层的，是：

- 参数读取
- 环境变量读取
- 路径拼接与路径拆解
- 文件读写、复制、重命名、删除
- 目录创建、目录清理
- 进程执行与输出捕获

这些能力的共同特点是：

- 它们本质上是宿主调用
- 不属于“AX 自己发明的高层抽象”
- 用 Rust 做实现不会削弱 AX 的价值

## 哪些能力不应该继续往 builtin 里塞

下面这些东西，原则上不应该优先写成 Rust builtin：

- “打包产物”
- “规范化文本”
- “清理输出目录后再生成报告”
- “扫描目录后按规则分类”
- “构建辅助流程编排”
- 任何明显属于工具策略层的多步逻辑

原因很简单：

- 这些已经不是宿主原语，而是组合逻辑
- 如果继续写在 Rust 里，AX 会退化成 builtin 壳
- 这些逻辑一旦能在 AX 层写，就应该尽量用 AX 写

所以当前的正确方向不是：

- 在 Rust 里继续写越来越厚的“伪标准库”

而是：

- 在 Rust 里只补必要原语
- 让 AX 样例和后续 AX 库去承接高层逻辑

## 新增 builtin 的准入规则

以后如果要再加一个 builtin，先过这四个问题：

1. 这个能力是不是宿主相关？
2. 如果没有它，AX 是否真的写不出下一类真实工具？
3. 它是不是原语，而不是三步以上的组合流程？
4. 加完以后，是否能立刻补一个更像真实工具的 AX 样例？

只要这四条里有两条以上答不上来，就先不要加。

## AX 层应该承接什么

一旦宿主原语已经到位，优先往 AX 层搬的应该是：

- 目录清单整理
- 文本重写规则
- 构建产物整理
- 命令执行编排
- 报告生成
- 小型 CLI 工具流程

也就是说：

- builtin 提供“能做什么”
- AX 代码决定“怎么做”

## 近期执行边界

当前阶段可以继续补的 builtin：

- 目录读取
- 更稳定的路径元数据
- 更细一点的文件状态查询
- 更可控的进程执行原语

当前阶段不应优先补的 builtin：

- 高层模板引擎
- 一整套文本处理 DSL
- 打包系统
- 模块级工具框架
- 大而全标准库叙事

## 最终目标

当前这些 builtin 不是 AX 的终态标准库。

它们更准确的定位是：

- AX 的宿主运行时边界
- AX 写真实工具时所需的最小外部原语
- 后续 AX 标准库和模块系统的地基

等 AX 的模块 / import / 库组织能力足够稳定后，应该逐步形成：

- Rust：宿主原语
- AX：高层库和工具逻辑

这才是对 AX 最有利的收口方式。
