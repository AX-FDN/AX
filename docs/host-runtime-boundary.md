# AX Host Runtime Boundary

最后更新：2026-04-24

这份文档只回答一个问题：

AX 当前哪些能力应该放在编译器内建宿主层，哪些能力应该留给 AX 自己去表达。

## 当前分层

AX 现在有两层：

1. Rust 宿主运行时
   位置：
   - `src/interpreter.rs`
   - `src/semantic/checker/builtin.rs`

   责任：
   - 接操作系统和宿主环境
   - 提供最小 builtin 能力
   - 给出稳定 diagnostics

2. AX 脚本层
   位置：
   - `examples/`
   - 后续真正的 AX 库代码

   责任：
   - 组合 builtin 做真实工具逻辑
   - 承担流程、规则、策略和报告生成
   - 尽量把“业务层”和“工具层”逻辑留在 AX 本身

一句话：

Rust 负责把宿主世界接进来。
AX 负责把这些原语组合成真正的工具。

## 哪些能力应该放在宿主层

只有这几类能力应该优先放在 builtin / host runtime 里：

- `argv`
- `env`
- `path`
- `fs`
- `process`
- 极少量基础 `string` 辅助

判断标准：

- 不接宿主就根本做不了
- 不先做这个原语，AX 连最小工具闭环都起不来
- 做成 builtin 后，能让 AX 层马上多写出一种真实工具样例

当前已经属于这一层的，是：

- 参数读取
- 环境变量读取
- 路径拼接与路径拆解
- 文件读写、复制、重命名、删除
- 目录创建、目录清理
- 进程执行与输出捕获

这些能力的共同特点是：

- 它们本质上是宿主调用
- 不属于“AX 自己发明的高层抽象”
- 用 Rust 做实现不会削弱 AX 的价值

## 哪些能力不应该继续往 builtin 里塞

下面这些东西，原则上不应该优先写成 Rust builtin：

- “打包产物”
- “规范化文本”
- “清理输出目录后再生成报告”
- “扫描目录后按规则分类”
- “构建辅助流程编排”
- 任何明显属于工具策略层的多步逻辑

原因很简单：

- 这些已经不是宿主原语，而是组合逻辑
- 如果继续写在 Rust 里，AX 会退化成 builtin 壳
- 这些逻辑一旦能在 AX 层写，就应该尽量用 AX 写

所以当前的正确方向不是：

- 在 Rust 里继续写越来越厚的“伪标准库”

而是：

- 在 Rust 里只补必要原语
- 让 AX 样例和后续 AX 库去承接高层逻辑

## 新增 builtin 的准入规则

以后如果要再加一个 builtin，先过这四个问题：

1. 这个能力是不是宿主相关？
2. 如果没有它，AX 是否真的写不出下一类真实工具？
3. 它是不是原语，而不是三步以上的组合流程？
4. 加完以后，是否能立刻补一个更像真实工具的 AX 样例？

只要这四条里有两条以上答不上来，就先不要加。

## AX 层应该承接什么

一旦宿主原语已经到位，优先往 AX 层搬的应该是：

- 目录清单整理
- 文本重写规则
- 构建产物整理
- 命令执行编排
- 报告生成
- 小型 CLI 工具流程

也就是说：

- builtin 提供“能做什么”
- AX 代码决定“怎么做”

## 近期执行边界

当前阶段可以继续补的 builtin：

- 目录读取
- 更稳定的路径元数据
- 更细一点的文件状态查询
- 更可控的进程执行原语

当前阶段不应优先补的 builtin：

- 高层模板引擎
- 一整套文本处理 DSL
- 打包系统
- 模块级工具框架
- 大而全标准库叙事

## 最终目标

当前这些 builtin 不是 AX 的终态标准库。

它们更准确的定位是：

- AX 的宿主运行时边界
- AX 写真实工具时所需的最小外部原语
- 后续 AX 标准库和模块系统的地基

等 AX 的模块 / import / 库组织能力足够稳定后，应该逐步形成：

- Rust：宿主原语
- AX：高层库和工具逻辑

这才是对 AX 最有利的收口方式。
